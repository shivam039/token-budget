# Performance

## TL;DR

Context management stays fast at large histories — including in a
realistic bounded-window scenario, not just a worst-case stress test.
Raw tokenizer throughput is a separate question with a separate,
honest answer: `token-budget-tiktoken` is not the fastest way to count
tokens, and that's fine, because counting tokens isn't what
`token-budget` is for.

All numbers below are generated by `bench/*.mjs`, not hand-typed — run
`npm run bench` yourself to reproduce them (or get numbers for your own
hardware). See [`bench/README.md`](../bench/README.md) for the full
methodology and environment details.

## Context-management benchmark

This is the actual product: given a growing message buffer, how long
does it take to derive what should remain in context. All three systems
below are given the **same simple length-based token counter**, so this
isolates buffer/eviction machinery cost — tokenizer speed is a separate
benchmark, further down.

### Realistic benchmark — bounded window on a large history

The shape most real chat apps actually run: a large accumulated history
(50,000 messages), querying a much smaller effective context window
(1,000–10,000 tokens) — not "keep almost the whole history," which the
stress test below deliberately does instead.

| Window (tokens) | token-budget (query only)\* | naive DIY (full rebuild)\* | LangChain `trimMessages` |
| --- | --- | --- | --- |
| 1,000 | 73.9 ms | 31.5 ms | 28,012 ms |
| 2,000 | 67.5 ms | 42.9 ms | 24,393 ms |
| 5,000 | 61.1 ms | 103.7 ms | 22,231 ms |
| 10,000 | 76.6 ms | 189.0 ms | 21,883 ms |

\* median of 10 trials (3 for naive DIY at every window, since each is a
full rebuild); LangChain's row is a single run per window — see
"Methodology" below for why, and `bench/README.md` for the general policy
on reduced trial counts.

**The finding this benchmark exists to surface:** `trimMessages`' cost
here doesn't shrink with a smaller window — it's driven by the
50,000-message history, not the ~35–357 messages actually retained. This
isn't cherry-picking an unfavorable window: it's the *smallest* windows
tested (1,000–10,000 tokens, well below the 50,000-token stress test
below) that show this most clearly, because that's exactly where a
window-size-driven algorithm should have looked fastest and didn't.

token-budget's row here times **only the query** (`setMaxTokens()` +
`getContextSync()`) against an already-built history, since the history
is built once and reused across all four window sizes — a fair
reflection of real usage, where the buffer accumulates once and the
effective window can change per turn without rebuilding history. Naive
DIY has no equivalent "requery an existing buffer at a new budget"
operation in its real-world form (the budget is baked into the per-add
eviction loop), so its numbers are a full rebuild each time — that gap
in capability is itself part of the finding, not an oversight in how it
was measured.

### Stress test — large, growing history against a large budget

The worst-case shape: a single 50,000-token budget applied against a
history that grows all the way up to (and past) that budget, so most of
the history is retained rather than aggressively trimmed.

| Messages | token-budget | naive DIY | LangChain `trimMessages` |
| --- | --- | --- | --- |
| 1,000 | 5.6 ms | 2.3 ms | 3.3 ms |
| 10,000 | 29.8 ms | 171.9 ms | 803.7 ms |
| 50,000 | 226.4 ms | 988.2 ms | ~19,500–40,900 ms\* |

\* LangChain's 50,000-message stress-test number showed real run-to-run
variance across separate benchmark sessions on the same hardware (from
~19.5s to ~40.9s) — reported as a range rather than a single number,
because presenting either end alone would overstate precision this
benchmark doesn't have at that extreme. Both ends are still 85–180×
token-budget's number at the same size; the realistic benchmark above is
the more representative comparison for everyday usage.

At small sizes (1,000 messages, nothing evicted yet) the three systems
are within a few milliseconds of each other — the gap only opens up once
real eviction work is happening at scale.

## Incremental accounting benchmark

Isolates one specific architectural claim: `addMessage()` does O(1)
amortized bookkeeping (count the new message, add it to a running total)
instead of recomputing the whole history's token count on every add. No
eviction happens in this benchmark (the budget is unbounded) — this is
purely the cost of keeping an accurate running total as messages arrive.

| Messages | token-budget (incremental) | naive recount (from scratch every add) |
| --- | --- | --- |
| 1,000 | 1.7 ms | 2.4 ms |
| 10,000 | 19.5 ms | 266.9 ms |
| 50,000 | 114.0 ms | 8,851 ms |
| 100,000 | 287.3 ms | 28,854 ms |

At 100,000 messages, naive recount takes **~100× longer** than
token-budget's incremental accounting — the cleanest, most directly
attributable result in this whole benchmark suite, because nothing else
(tokenizer choice, strategy, eviction) is involved.

## Raw tokenizer benchmark

**This is not a flattering result for `token-budget-tiktoken`, and it's
published anyway.** Counting tokens and deciding what should remain in
context are different jobs — see [`comparisons.md`](./comparisons.md).

Same text, same encoding family (`o200k_base` — `gpt-tokenizer`'s own
default, not tilted toward `token-budget`'s choice).

**Bulk-encode one large corpus (~88,000 tokens, warm):**

| Tokenizer | Median | Throughput |
| --- | --- | --- |
| `gpt-tokenizer` | 15.4 ms | 5.7M tok/sec |
| `token-budget-tiktoken` | 168.8 ms | 521k tok/sec |
| `llm-token-counter` | 390.4 ms | 225k tok/sec |

**Many short messages, one call each (n=2,000 for the two fast ones):**

| Tokenizer | Median (total) | Per call |
| --- | --- | --- |
| `gpt-tokenizer` | 6.5 ms | 3.3 µs |
| `token-budget-tiktoken` | 71.7 ms | 35.8 µs |
| `llm-token-counter` (n=50 — see note) | 13,065.7 ms | ~261,300 µs |

`llm-token-counter` calls real `tiktoken`'s `encoding_for_model()` — a
fresh WASM encoder instantiation — and frees it on **every call**, with
no caching. At n=2,000 (the same sample size as the other two) that made
the benchmark impractically slow to finish, so its sample size is
deliberately much smaller (n=50) — the per-call cost, not the total, is
what the comparison is about, and it's large enough that a smaller
sample still makes the point honestly.

**Read this as:** `gpt-tokenizer` is a genuinely faster pure-JS
tokenizer than `js-tiktoken` (what `token-budget-tiktoken` wraps) — by
design, `token-budget-tiktoken` prioritizes portability and compatibility
with the wider `js-tiktoken` ecosystem, not raw throughput. If tokenizer
speed alone is your bottleneck, `gpt-tokenizer` may be the better choice
— you can still use it as `token-budget`'s `tokenizer` option (anything
with a `count(text)` method works).

## Methodology

- **Hardware/software**: see [`bench/README.md`](../bench/README.md) —
  Node v22.22.2, Ubuntu 24.04, 4 vCPU Intel Xeon @ 2.80GHz. Re-run
  `npm run bench` for numbers on your own hardware.
- **Versions**: `gpt-tokenizer@4.0.0`, `llm-token-counter@1.0.0`,
  `@langchain/core@1.2.9`, `token-budget`/`token-budget-tiktoken` at this
  repo's current commit (not yet a published version).
- **Iterations**: every script warms up (discarded) before timing, then
  runs multiple trials and reports **median and p95**, not a single run
  — see [`bench/lib/stats.mjs`](../bench/lib/stats.mjs). Trial counts are
  reduced at the largest, genuinely slow input sizes (LangChain's
  `trimMessages` at 50k messages, naive recount at 100k messages) to keep
  the whole suite finishable in a few minutes; every script states in its
  own output, at the point it happens, exactly when and why — nothing is
  silently thinned out to hide variance.
- **Fairness**: every buffer/eviction benchmark gives all systems under
  test the same simple token counter, so results measure buffer/eviction
  machinery, not tokenizer choice. The realistic benchmark's fairness
  argument is stated inline above, not just asserted.

## Reproduce

```sh
npm install
npm run build          # builds token-budget and token-budget-tiktoken
npm run bench            # runs every bench/*.mjs script in sequence

# or one at a time, from inside bench/:
npm run bench:incremental
npm run bench:context
npm run bench:context:realistic
npm run bench:tokenizer
```
