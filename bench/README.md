# bench/

Reproducible performance benchmarks for `token-budget`, run against real
competitors on identical inputs. Not published to npm (`private: true`) —
this exists for repo contributors and anyone verifying the numbers in
[`docs/benchmarks.md`](../docs/benchmarks.md), not as a package.

## Running

```sh
npm install          # from the repo root — installs this workspace's devDependencies too
npm run build         # builds token-budget and token-budget-tiktoken, which bench resolves as workspace packages
npm run bench          # runs every bench/*.mjs script in sequence
```

Or run one script at a time from inside `bench/`:

```sh
npm run bench:incremental        # incremental-accounting-bench.mjs
npm run bench:context             # context-management-bench.mjs (stress test)
npm run bench:context:realistic   # context-management-realistic-bench.mjs (bounded window)
npm run bench:tokenizer           # tokenizer-bench.mjs
```

Numbers are generated by these scripts every time — nothing in
`docs/benchmarks.md` is hand-typed. If you get different numbers than
what's documented there, your hardware is different (expected — see
below), or something regressed (not expected — please open an issue with
your output).

## Methodology notes

- Every script uses [`lib/stats.mjs`](./lib/stats.mjs)'s `measure()`/`measureAsync()`:
  a warmup phase (discarded) followed by N timed trials, reporting
  **median and p95**, not a single run and not a cherry-picked best.
- All buffer/eviction benchmarks (`context-management-*`,
  `incremental-accounting-bench.mjs`) give every system under test the
  **same simple length-based token counter** — this isolates
  buffer/eviction machinery cost, not tokenizer speed. Tokenizer speed is
  its own, separate benchmark (`tokenizer-bench.mjs`) for exactly this
  reason.
- Trial counts are reduced at the largest input sizes for genuinely slow
  cells (LangChain's `trimMessages` on 50k messages, naive O(n²) recount
  at 100k messages) to keep the whole suite finishable in a few minutes.
  Every script states in its own output, at the point it happens, when
  and why a reduced trial count was used — nothing is silently thinned
  out.
- Fixtures live in [`fixtures/messages.mjs`](./fixtures/messages.mjs) so
  every script benchmarks the same shape of data.

## Why these three competitors specifically

- **`gpt-tokenizer`** and **`llm-token-counter`** — real, published npm
  packages solving pieces of the same general problem space (token
  counting). Comparing tokenizer speed against them is a fair, like-for-like
  test.
- **LangChain's `trimMessages`** — the built-in message-trimming utility
  most likely to be the actual alternative for someone evaluating
  `token-budget` who's already using LangChain.js.

None of these are being disparaged for existing or for doing what they're
built for — see [`docs/comparisons.md`](../docs/comparisons.md) for the
positioning (`gpt-tokenizer` answers "how many tokens"; `token-budget`
answers "what should remain in context").
